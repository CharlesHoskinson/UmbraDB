# UmbraDB 0.9.5 "Penumbra"

UmbraDB is a local, single-writer datastore for Midnight clients: wallets, dev tooling, and anything
else needing durable, versioned, content-addressed storage. It is a library, not a server. You supply
a PostgreSQL instance and a connection string, and UmbraDB owns its schema inside it, talking to
Postgres through postgres.js with no ORM.

This is the first npm release.

Requires Node 24 or later. Tested against PostgreSQL 17, and the schema uses syntax introduced in
PostgreSQL 15. No lower bound has been verified, so treat anything below 15 as unsupported.
Apache-2.0.

## The fix this release exists for

`CheckpointStore.save()` could not join a caller's transaction. A watermark could commit ahead of the
checkpoint it pointed at, and a crash between the two left the next start resuming from a cursor
whose data was never durable. You get no error and no visible corruption. You just lose history.

`saveAndAdvance` writes the checkpoint and advances its watermark in one transaction.

```ts
import { saveAndAdvance } from "umbradb";
await saveAndAdvance(sql, { checkpoint, watermark });
```

### If you are upgrading

`save()` takes an options object and accepts a transaction handle. A call that relied on the old
signature must pass the handle through, or move to `saveAndAdvance` if it was pairing a save with a
watermark write:

```ts
// before
await store.save({ walletId, networkId, data });
await watermarks.set(kind, key, cursor);

// after
await saveAndAdvance(sql, { checkpoint: { walletId, networkId, data }, watermark: { kind, key, cursor } });
```

Migrations are forward-only. There is no down-migration, so rolling back a version means restoring a
backup taken before the upgrade.

## Installing

```bash
npm install umbradb
```

```ts
import { createClient, runMigrations, PgTemporalKV } from "umbradb";

const sql = createClient({ connectionString: process.env.DATABASE_URL });
await runMigrations(sql);

const kv = new PgTemporalKV(sql);
await kv.put("wallet:balance", { night: "2000" });
const latest = await kv.get("wallet:balance");
const earlier = await kv.getAt("wallet:balance", { version: 3n });
```

Everything imports from the package root. The `exports` map exposes a single `"."`, so a deep import
into an internal module fails with `ERR_PACKAGE_PATH_NOT_EXPORTED`. If you cannot import it from the
root, it is unsupported and can change without notice.

## The surface

`TemporalKV` is a versioned key-value store. Every `put` appends a version and nothing is overwritten
in place. Passing `expectedVersion` makes the write a compare-and-swap that raises
`VersionConflictError` on mismatch. Point-in-time reads are addressable by version or by wall-clock
timestamp. History is prunable, and a read for a pruned version raises `HistoryUnavailableError`, so
you can tell an unavailable answer from a wrong one.

`CheckpointStore` stores large snapshots as content-addressed 4 MiB chunks. A global chunk pool means
identical chunks are stored once across all wallets. Each save writes a manifest whose hash is
computed at write time and re-verified on load. Garbage collection prunes manifests, then reclaims
unreferenced chunks after a 15-minute grace window. Without that window, GC can reclaim a chunk that
an uncommitted save is about to re-reference. A save that stays open longer than the window can lose
a chunk it expected to reuse. Reads run in REPEATABLE READ and stay consistent against a prune
committing concurrently.

`Watermarks` stores sync cursors, last-write-wins and unversioned, since a cursor has no history
worth keeping. One table, `fillfactor = 90`, no secondary index. Do not add one. An index there
breaks HOT update eligibility and bloats the busiest write path in the system. Large integers cross
the boundary as decimal strings, so a block height cannot lose precision passing through JavaScript.

`Transaction/Lease` composes the other modules. `withTransaction` runs any mix of primitives inside
one PostgreSQL transaction on one connection, so they commit or roll back together. `acquireLease`,
`tryAcquireLease`, `releaseLease` and `withLease` give single-writer coordination through
connection-pinned advisory locks, held for the life of the connection, with no TTL and no stealing.
If the body of `withLease` succeeds and the release then fails, the caller gets an `AggregateError`
carrying both.

`TransactionHistory` stores per-wallet transaction history with lifecycle-aware upsert and merge,
GIN-indexed on a denormalized identifiers array. It implements the shape the Midnight wallet SDK's
`TransactionHistoryStorage` expects.

`PgWalletStateEnvelopeStore` persists a whole wallet-sync snapshot in one `CheckpointStore.save()`.
It adds no table and no migration of its own.

## Durability

`runMigrations` runs a startup probe. It checks `fsync`, `synchronous_commit` and `full_page_writes`,
and makes a best-effort attempt to detect a transaction pooler in front of Postgres, because a pooler
breaks the session-scoped advisory locks the lease depends on. A violation raises
`DurabilityContractError` or `TransactionPoolerDetectedError` at startup.

Server-side `statement_timeout`, `lock_timeout` and `idle_in_transaction_session_timeout` are set,
and the migration lock acquire is bounded by a transaction-scoped `SET LOCAL`, raising
`MigrationLockTimeoutError` instead of hanging.

The crash suite tests this. It kills the client process, and separately kills Postgres, mid-save,
including an unclean postmaster kill by SIGQUIT followed by crash recovery, under both
`synchronous_commit = on` and `off`. Under `off`, the suite accepts a lost tail of acknowledged
commits but fails on an inverted durability order. These tests are required in CI and cannot be
skipped silently.

A re-runnable benchmark lives in `bench/`, covering KV throughput, checkpoint save and load, dedup
ratio, GC duration measured to one million chunks, and lease contention. It publishes no target you
should plan against, since the numbers came off our hardware. Documented ceilings are in
`Performance/CEILINGS.md`. The committed baseline artifact is still named for the change set that
produced it, `baseline.1.0.0-perf-baseline.1.json`, which is a filename and not a version claim.

## Errors

Failures that UmbraDB itself raises are `StorageError` subclasses with a stable `code` and a
machine-readable `retryable` field. There are 24 codes. Four are retryable: `CONNECTION_ERROR`,
`TRANSACTION_FAULT`, `LEASE_TIMEOUT` and `MIGRATION_LOCK_TIMEOUT`.

```ts
try {
  await kv.put(key, value);
} catch (e) {
  if (e instanceof StorageError && e.retryable) {
    // safe to retry
  }
}
```

Two things escape that check. The `AggregateError` from a failed `withLease` release is a plain
JavaScript error, and driver failures occurring before UmbraDB's wrappers are established arrive
untranslated. Handle both.

A drift test derives `docs/ERROR-CATALOG.md` from the exported classes with no hard-coded count and
fails CI when catalog, changelog and surface disagree, so the published table cannot drift from the
code.

Known limitation: PostgreSQL `28xxx` authentication failures surface as a retryable
`ConnectionError`. A wrong password therefore looks transient, and an unbounded retry loop will
hammer it, which can trip account lockout. Cap your retries and your backoff. A distinct
`AuthenticationError` is a 1.1 candidate, left out of 0.9.5 to keep the frozen surface unchanged.

## What is proved, and what that is worth

`Formal/STORAGE_ALGEBRA.md` states nine laws, two of which split, giving eleven obligations.

Four are proved in Lean 4 under a CI gate that scans the tree for `sorry`, `admit`, `axiom` and
`unsafe`, then builds and independently re-checks every declaration. They are T3 temporal projection,
T5 coherence, W1 last-write-wins, and C1, which says chunk deduplication cannot lose data whatever
order chunks arrive in. Theorems about T1 per-key ordering, T2 compare-and-swap and T4
dual-addressing also live in the tree and pass the same gate, but they sit outside the frozen set, so
treat them as work in progress rather than commitments.

Three obligations have tests and no proof. C2a garbage-collection safety and L1 lease mutual
exclusion are covered by property tests against real Postgres. C2b eventual collection has its
mechanism tested but not its liveness claim, because a property test observes a bounded prefix and
cannot tell "eventually" from "never". Cross-writer T1 is open in the specification.

Two limits define what the proofs are worth.

Zero `sorry` certifies depth, not breadth. The gate checks that every stated law is proved. It cannot
notice a law nobody stated.

**Nothing connects the proofs to the shipped code.** No theorem relates any Lean definition to the
SQL DDL, a trigger, `clock_timestamp()` or the TypeScript adapter. The proofs constrain the design.
They do not constrain the package you install. Ten property tests running against real Postgres
through Testcontainers are the only evidence that the implementation follows the model, and a passing
test is not a proof.

## Security

Read `SECURITY.md` before deploying.

The threat model assumes a single trusted writer.

`schema` is namespacing and not an isolation boundary. Do not use it to separate mutually distrusting
parties.

There is no encryption at rest. Anyone who can read the Postgres data files, a backup, or a replica
reads your data in clear text. Encrypt the disk before storing anything you care about.

Cross-wallet deduplication is a side channel, since a global chunk pool reveals whether an identical
chunk already exists. Exploiting it under the single-writer model requires already being the writer.
Per-wallet keyed chunking is a 1.1 item.

Supply-chain checks run in CI: pinned installs with lifecycle scripts disabled, a blocking `npm
audit`, full-history secret scanning, and container scanning of digest-pinned images.

## What this is not

An ORM or query builder. A distributed or multi-node store. A multi-tenant one. A chain indexer,
since it stores what a client gives it and stays indexer-agnostic. Encrypted at rest.

Full-chain archival storage exists in the tree but is excluded from the published surface. It ships
in 1.1, alongside `AuthenticationError` and per-wallet keyed chunking.

## Compatibility, and what 1.0.0 needs

The surface is enumerated and drift-tested. The SemVer promise not to break it does not bind until
1.0.0, because `0.y.z` guarantees nothing. Treat 0.9.5 as the release candidate for that promise.
Depend on it and report what breaks. We intend to ship 1.0.0 with this surface unchanged, and a
forced change will appear in the changelog under a heading saying so.

One thing stands in the way. UmbraDB has so far been run end to end only against a hosted indexer,
where a funded wallet synced, persisted its envelope, was killed, and resumed from its durable cursor
with no drift. Everything else has landed: the surface freeze, the durable checkpoint cursor,
recovery testing, the performance baseline and the security sign-off. Until it runs the same way on a
stack we operate ourselves, from archive node through local indexer to UmbraDB, this stays at 0.9.

A penumbra is the partial shadow you cross just before totality. Hence the name, and hence 1.0.0's.
